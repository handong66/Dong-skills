# Runtime recovery

The installed integration owns command names, flags, state locations, completion fields, and supported configuration values. Read its current documentation/schema before operating it. Do not preserve an old cache path, timeout constant, or service-tier workaround as a permanent rule.

1. **Was a job submitted?** Retain its job/session handle. A tracked wrapper returning a handle is not task completion. If the wrapper failed, inspect its job record before resubmitting to avoid a duplicate writer. Absence from one partial listing is not sufficient proof that nothing started.
2. **Is it still running?** Use the documented status/result/wait route and keep the task visible. A wrapper notification may mean only that forwarding ended. Read the final answer, not just a terse summary or log tail. Stop polling a terminal record; distinguish completed, partial, failed, cancelled, and no evidence.
3. **Can existing work be recovered?** Prefer a supported continuation/finalization when it preserves the intended scope and write mode. Diagnose authorization, quota, network, workspace, and budget failures separately. Silence alone is not grounds to cancel a job doing a long build or test.
4. **Did requested settings take effect?** Preserve explicit model, effort, and speed preferences. Use the integration's returned effective settings or authorized, narrowly scoped job metadata to verify them. If the wrapper cannot forward a required setting, use only a documented fallback within the same authorization; retain lifecycle tracking. Never forward raw runtime records to another agent.
5. **Is the active runtime current?** Verify the actual process/binary version before changing configuration. Installing a CLI does not prove a resident runtime restarted. Use the supported restart mechanism; if a process restart is necessary, identify the owned job/process and its effects first. Never kill broad broker/CLI patterns or disrupt unrelated sessions.
6. **Is the workspace wrong?** Inspect the resolved root. Rescope through a supported authorized workspace or explicitly hand the work to the other host. An out-of-root file does not permanently assign authorship to one model, and a path refusal must not be bypassed through an unguarded invocation.

A prior EPERM failure does not establish that Codex cannot run tests today. Check the required command on the current host. A startup error does not establish today's valid `service_tier` values; read the actual error and supported configuration before changing them. Report blocked verification honestly and retain the user's settings.
