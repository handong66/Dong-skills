# Recovery, isolation, and conversations

The installed agy plugin owns the runtime contract, typed failures, result fields, and failure-routing table. Read those current references; measured behavior from one CLI version is not a permanent capability rule. Use structured results and warnings rather than a potentially omitted text duplicate.

## Confirm workspace and isolation

Inspect the resolved workspace and selected mode before dispatch. The plugin validates workspace access; do not bypass a refusal through a shell invocation. A successful process exit does not prove that the intended directory was inspected.

For review and adversarial review, the current plugin makes a disposable copy from Git's file list. Ignored dependencies, build outputs, and private files may be absent. Check a reported missing file against the real authorized tree before accepting or rejecting the finding. Provide necessary sanitized evidence if the copy cannot contain it.

This copy separates review edits from the source repository; it is not OS confinement. Do not disclose the real repository path or private paths in the review prompt. If the reviewer edits its copy, those edits are not a fix applied to the real tree. Use an authorized implementation packet and verify the real diff to apply a repair.

Read isolation warnings. If the real tree or HEAD changed during the review, inspect the change and re-pin affected claims; the warning alone does not establish who caused it. A denied read or missing target means no evidence for that portion of the review.

## Read results and recover

1. Keep the job/conversation handle. Use the plugin's advertised conversation listing for lost handles, respecting its workspace scope and coverage limits; it is a record of plugin-started work, not all CLI history.
2. Separate submission, job state, CLI outcome, answer completeness, and inspected evidence. Follow the plugin's finality predicate. A success label or tool count alone is not a verified review.
3. Read the final-answer view, not a stdout tail. Retain partial answers and warnings, but do not count them as completed conclusions. Do not repeatedly poll a terminal record.
4. Follow current failure routing. A provider stall with no useful work is different from a spent budget after substantive progress. Preserve explicit model/effort preferences and inspect the observed model when available. Do not cancel on elapsed time or silence alone.
5. Resume a known implementation conversation only when the plugin says it is recoverable and the original write authority still applies. Verify returned conversation identity; a fallback fresh conversation lacks earlier context.
6. Never continue an isolated review through generic continuation: isolation belongs to the run, and generic continuation is write-capable. Use a fresh isolated review with a narrowed remaining question and necessary authorized evidence.

Before replacing a writer, confirm stop/completion and inspect its diff. A cancelled job is not necessarily resumable; use the current contract rather than assuming it retained a conversation.

## Review verdict

Use the plugin's deduplicated evidence counters and warnings, but verify the actual cited target. No inspected evidence means no passing review; a concrete visual claim still needs inspection of the intended artifact/region. Resolve disagreements with source and independent probes, not model votes. Out-of-model findings stay advisory under the stated threat model; verified in-scope blockers remain open until resolved, regardless of review budget.
